# Submit, errors and disabled Fields

## Submitting

`submit()` is asynchronous and returns a sealed result. Handle both cases with an exhaustive `switch`:

```dart
final result = await form.submit();
switch (result) {
  case FormidableSubmitValid(:final value):
    await api.signUp(value);
  case FormidableSubmitInvalid(:final errors):
    // Every invalid Field and Field Array, keyed by its typed handle.
    print(errors[form.email]);
    print(errors[form.members]); // a Field Array, e.g. MinItems
}
```

`errors` is one map in tree order. Its keys are the handles of the Fields and of the Field Arrays that have errors; a Field Array comes before the Fields of its items. The errors of a Field Array are the errors of the array itself (a minimum number of items, an empty required array), never the errors of its items.

Before it decides, `submit()`:

1. clears the errors applied to the Form as a whole;
2. marks **every** Field as touched and submitted, so every error can show. Nothing else can mark a Form as submitted, because the method that does it is internal;
3. waits for every pending [Async Validator](/validation/async), so it never decides on an unchecked value;
4. when the Form is invalid, focuses the **first invalid Field in Schema declaration order**. Fields that are disabled or not shown by any widget are skipped.

Formidable does not track your own side effects, so there is no "submitting" state. The `pending` status is about checks that run on the Fields, not about your request.

The declarative pattern drives a button from a Form Selector over `state.meta.valid` and uses `form.value` in the tap handler: `valid` is false while a check runs, so the button waits for it. A disabled button hides the reasons for invalidity until the user touches the Fields, so prefer an enabled button plus `submit()` when the user needs to see what to fix.

## When errors are shown

An error is shown when the policy says so:

| Policy | Errors show |
| --- | --- |
| `FormidableErrorDisplay.touched` (default) | once the Field is touched, that is, the user left it |
| `FormidableErrorDisplay.dirty` | as soon as the value or presence differs from the initial state |
| `FormidableErrorDisplay.submit` | only after `submit()` |

Under every policy, `submit()` shows every error. Set the policy for the whole app on the config, and for one Form on its Form Scope. The Form Scope wins; a single widget can still override both.

```dart
FormidableConfig(
  errorDisplay: FormidableErrorDisplay.dirty,
  child: ...,
);

SignUpFormScope(
  errorDisplay: FormidableErrorDisplay.submit,
  child: ...,
);
```

The policy only decides what the widgets show. `state.meta.errors`, `state.meta.status` and `submit()` always see every error.

## Applying errors

Use `applyErrors` for errors only a server can find:

```dart
form.applyErrors(
  fieldErrors: {
    form.username: [const UsernameTakenError()],
  },
  formErrors: [const ServiceUnavailableError()],
);
```

- Field errors are added after the errors of the Field's Validators and make the Field, and the Form, invalid. They **clear on the next change to that Field's value or presence**. Writing the same value, or touching the Field, does not clear them.
- Form errors belong to the Form as a whole. They show in `form.state.meta.errors`, make the Form invalid, and clear on the next change to any Field and when `submit()` starts.
- Show them like any error: register messages for your own error classes in `FormidableConfig.messages`.

### Errors that depend on other Fields

A server can reject a combination of values and not one of them. When it rejects the credentials, the error belongs on the password, but the user can fix it by changing the URL or the username instead, and the error must not stay on a password that was never wrong. `Field.applyErrors` takes a `clearOn` list for it:

```dart
form.password.applyErrors(
  const [RejectedByServerError()],
  clearOn: [form.url, form.username],
);
```

The errors go away on the next change of the value or presence of the Field itself, as before, and also on the next change of any listed node: a Field, a Nested Form or a Field Array of the same Form (a change anywhere below a Nested Form or a Field Array counts). Touching or focusing a listed node does not clear them. Applying errors again replaces the previous list and its `clearOn`, and the Form releases what it listens to when the errors go away and when it is disposed. A Field that lists itself is ignored. The map shape `form.applyErrors(fieldErrors: ...)` has no `clearOn`: call `applyErrors` on the Field when you need it.

## Disabled Fields

```dart
form.discount.disable();
form.discount.enable();
```

A disabled Field keeps its value and still contributes to the output, but its Validators and applied errors are skipped, and the widget does not accept input. It still follows the presence rules: a required Field that is Unset blocks submit even when disabled, because no valid output would exist.

`state.enabled` tells you the current state, and `field.focus()` does nothing while a Field is disabled.

### Disabling a whole Form

`disable()` and `enable()` exist on a Form, a Nested Form, a Field Array and a Dynamic Form too. Use them while a request is in flight, or for a read-only view:

```dart
form.disable(); // every Field below is disabled, none of them is changed
try {
  await api.signUp(signUp);
} finally {
  form.enable(); // undoes the disable() above, even if the request failed
}
```

The example assumes that the Form was enabled before the request: `enable()` does not remember an earlier `disable()` of the same Form, so a read-only Form should not go through it.

A container has its own `enabled` flag, a separate layer from the flags of the Fields. A Field is effectively enabled only when its own flag and the flag of every container above it are set, and `state.enabled` of a Field reports that. The Fields are never written, so `enable()` restores exactly the previous state: a Field that a Form Effect or your code had disabled stays disabled. An effectively disabled Field behaves like any disabled Field, with the rules above, so the widgets need no change. The lock reaches items added to a Field Array later and Fields registered in a Dynamic Form later.

Read the flag of a container from its state: `form.state.meta.enabled` for a Form or a Nested Form, `form.phones.state.enabled` for a Field Array. A Nested Form or a Field Array inside a disabled Form reports false too. One call is one notification, and a call that changes nothing notifies nothing.
