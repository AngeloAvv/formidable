# State snapshots and reactive widgets

Every Field, Field Array and Form holds an immutable **state snapshot** and notifies its listeners synchronously when that snapshot changes. Imperative code can follow it through [streams](#streams) that only emit for what it cares about. The snapshot of a Form is complete: it holds the state of everything below it, so a change anywhere, a typed character included, gives a state that is different from the previous one. Builders have the current snapshot from the first frame, so there is no empty first build. Formidable does not depend on bloc, but the widgets work the way you would expect from `flutter_bloc`.

## Field state

`form.username.state` is a `FormidableFieldState<T>`:

| Member | Meaning |
| --- | --- |
| `value` | The chosen value, typed `T`. It throws a `StateError` while the Field is Unset, so check `defined` first |
| `valueOrNull` | The chosen value, or null while the Field is Unset. On a nullable Field it cannot tell Unset from a chosen null, `defined` does |
| `defined` | Whether the Field holds a value. Tells Unset apart from a chosen null |
| `valid` | Whether the Field can be submitted now: no errors and no check running. It is `status == valid` |
| `status` | `invalid` while there are errors, else `pending` while a check runs, else `valid` |
| `errors` | Every Validation Error of the Field |
| `touched` | The user interacted with the Field and left it |
| `dirty` | The value or presence differs from the initial state. Going back to the initial state makes the Field clean again |
| `enabled` | Whether the Field takes part in the Form. It is false when the Field was disabled, and also while a Form, Nested Form, Field Array or Dynamic Form above it is disabled, see [the container lock](/form/submit#disabled-fields) |
| `submitted` | The Form was submitted since the Field was created |
| `pending` | An [Async Validator](/validation/async) is still checking the value |

A Field Array state (`form.phones.state`) has `status`, `valid`, `dirty`, `pending` and `enabled`. It is `valid` when the array and every item have no errors and no check is running, and `enabled` is the flag of the array, false while the array or a container above it is disabled.

A Dynamic Form state (`form.answers.state`) has `status`, `valid`, `dirty`, `pending` and `enabled`, derived from every Field and Nested Form registered in it.

`pending` is a status of its own. A node with no errors and a check still running is neither `valid` nor `invalid`: it cannot be submitted yet, and it has no error to show. See [ADR 0006](https://github.com/AngeloAvv/formidable/blob/main/docs/adr/0006-form-lock-valid-means-submittable-and-value-throws.md).

Flags are read from the state, never from the handle: `form.email.state.valid`, `form.state.meta.dirty`. A Field, a Field Array or a Form offers actions (`setValue`, `clear`, `touch`, `untouch`, `enable`, `disable`, `reset`, `commit`, `submit`...) plus `value`, `valueOrNull` and `defined`, which stay on the handle because they are current even while [Form Effects](/form/effects) run, unlike `state`. See [ADR 0005](https://github.com/AngeloAvv/formidable/blob/main/docs/adr/0005-flags-are-read-from-the-state.md).

## Form state

`form.state` is typed after the Form. The generator writes one state class per Schema, for example `SignUpFormState`, and `SignUpForm.state` returns it. It extends `FormidableFormState`.

The metadata of the Form is under `state.meta`, a `FormidableFormMeta<SignUp>`. The Fields live next to it, so a Schema field can be called `status`, `dirty`, `pending` or `errors` without hiding anything. The generic `FormidableFormState`, used by the widgets that do not know the Schema, has the same `meta`, so `state.meta.status` reads the same either way.

| Member of `state.meta` | Meaning |
| --- | --- |
| `valid` | Whether the Form can be submitted now: no Field has errors and no check is running. It is `status == valid` |
| `status` | `invalid` while any Field has errors, else `pending` while any check runs, else `valid` |
| `dirty` | Any Field is dirty |
| `pending` | Any Field is still waiting for the result of an [Async Validator](/validation/async) |
| `enabled` | False while the Form is disabled, or while a Form above it is. The Fields have their own `enabled`, see [the container lock](/form/submit#disabled-fields) |
| `errors` | Errors of the Form as a whole, not tied to a Field |
| `defined` | False only for an optional [Nested Form](/schema/nested-forms) that is Unset |
| `value` | The Schema instance, typed `SignUp`. It throws a `StateError` unless the Form is valid and set, so it is never null. It is lazy, see below |
| `valueOrNull` | The Schema instance while the Form is valid and set, null otherwise |

And, on the generated state, one member per child, with the name of the Schema field (the name `meta` is the only one a Schema field cannot use):

| Child | Type of its member |
| --- | --- |
| A Field | `FormidableFieldState<T>` |
| A Passthrough Field | its value, `T` |
| A Nested Form | the generated state of that Form, for example `AddressFormState` |
| A [Field Array](/schema/field-arrays) | `FormidableFieldArrayState<S>`, where `S` is the state of an item: `PhoneFormState` for Nested Forms, `FormidableFieldState<String>` for Fields |
| A [Dynamic Form](/schema/dynamic-forms) | `FormidableDynamicFormState`, which holds the state of what is registered, by key |

```dart
final state = form.state; // SignUpFormState
state.username.valueOrNull; // String?
state.address.street;       // FormidableFieldState<String>, in a Nested Form
state.phones.items.first;   // PhoneFormState, in a Field Array
state.meta.status;          // FormidableStatus: valid, invalid or pending
state.meta.valueOrNull;     // SignUp?
```

Equality is deep. Editing an item of a Field Array, adding, removing or moving one, or changing a Field of a Nested Form gives a state that is `!=` to the previous one. `state.meta.valueOrNull` does not take part in equality: it is derived from the states of the children, and a Schema is not required to define `==`.

### The value is lazy

The Schema constructor does not run when a state is published, so typing in a Field does not build a Schema nobody reads. `state.meta.value` (and `valueOrNull`) builds it from the states of the children on the first read, caches it, and gives the same instance on every later read of that state. Because it is built from the state and not from the live Form, a state you kept still gives the value it had, even after the Form moved on.

`form.value` is the `state.meta.value` of the current state, and `form.valueOrNull` its `valueOrNull`. `value` throws unless the Form is valid, and that includes while it is pending, so read it only where the Form is known to be valid, for example in the handler of a button that follows `state.meta.valid`. Everywhere else, read `valueOrNull`:

```dart
final signUp = form.valueOrNull;
if (signUp != null) save(signUp);
```

## Notifications

A Field, a Field Array or a Form calls its listeners synchronously and only when its state is different from before. Because the state of a Form holds every child, `form.addListener` fires on every change below it: a value, `touched`, an error, an item added to an array. All of them have the shape of Flutter's `ValueListenable` (`state`, `addListener`, `removeListener`); `asValueListenable()` adapts them:

```dart
ValueListenableBuilder(
  valueListenable: form.username.asValueListenable(),
  builder: (context, state, _) => Text('${state.valueOrNull}'),
)
```

## Streams

`addListener` is the low-level channel: it fires on every state change, which is what a widget wants and what imperative code rarely does. Searching when a text Field merely lost focus, or planning a route again when a Form was touched, are the usual surprises. Every Field, Form, Nested Form, Field Array and Dynamic Form therefore has four streams that listen for you and only wake you up for what you ask for:

| Stream | Emits |
| --- | --- |
| `changes` | The full state, on every state change. The stream form of `addListener` |
| `valueChanges` | Only when the value changes, see the table below |
| `statusChanges` | A `FormidableStatus`, only when it changes between `valid`, `invalid` and `pending` |
| `select<R>(selector)` | What `selector` picks from the state, only when it changes (`==`) |

What `valueChanges` means and what it emits depends on the node:

| Node | Emits when | Event |
| --- | --- | --- |
| Field | its value or presence changes | the value, `T?` |
| Form, Nested Form | the value or presence of any Field below it changes, Nested Forms, Field Arrays and Dynamic Forms included | the state of the Form, typed after the Schema (`SignUpFormState`) |
| Field Array | an item is added, removed, moved or edited | `FormidableFieldArrayState<S>` |
| Dynamic Form | a Field is registered or removed, or the value or presence of one changes | `FormidableDynamicFormState` |

Touching a Field, submitting, focus, errors and `pending` are state changes, not value changes: they reach `changes` and `select`, never `valueChanges`. The event of a Form is its state and not the Schema instance on purpose. The Form has no value until it is valid, and a Form that becomes valid because a server error went away or an async check finished has no new value, so `valueChanges` does not follow `form.value`. Read `state.meta.valueOrNull` in the listener when you want the Schema instance.

For a Field the event is `null` both when the Field becomes Unset and when null is chosen on a nullable Field, so going from one to the other emits `null` again. Read `field.defined` in the listener to tell them apart, see [Unset is not null](/schema/presence#unset-is-not-null).

`select` is the general tool. It computes the selection when you subscribe, so the first event is a real change, and it compares with `==`, so a record or a value class works:

```dart
// Plan the route again only when the stops change, not when the Form is touched.
final subscription = form
    .select((state) => (state.from.valueOrNull, state.to.valueOrNull))
    .listen((stops) => planRoute(stops.$1, stops.$2));
```

On a generated Form the streams are typed after the state: `form.valueChanges` is a `Stream<SignUpFormState>`, and the selector of `form.select` receives a `SignUpFormState`.

The streams are driven by the same state as the listeners, so they behave the same way:

- They are **broadcast and synchronous**: the event arrives right after the change, before the write returns, and any number of listeners can subscribe. A listener that writes to the Form from inside an event sees its own change delivered right after the current event, in order, never nested.
- They **never emit the initial state**: the state at the time you listen is the baseline.
- They **listen to the node only while they have subscribers** and cost nothing otherwise. Cancel the subscription when you are done, and `form.hasListeners` tells whether anything is still listening.
- They **close when the node is disposed**, so `onDone` runs and a `StreamSubscription` needs no manual clean-up for that.
- A batch (`patch`, `replace`, `reset`, `batch`) is one change, so it is one event.

### Search as you type

A Field's `valueChanges` ignores everything that is not a value, so it is the right input for a search box. A debounce is a few lines of plain Dart, and does not need an extra dependency:

```dart
final class QuerySearch {
  QuerySearch(this.form, this.search) {
    _subscription = form.query.valueChanges.listen(_onQuery);
  }

  final SearchForm form;
  final void Function(String? query) search;
  late final StreamSubscription<String?> _subscription;
  Timer? _debounce;

  void _onQuery(String? query) {
    _debounce?.cancel();
    _debounce = Timer(const Duration(milliseconds: 300), () => search(query));
  }

  void dispose() {
    _debounce?.cancel();
    _subscription.cancel();
  }
}
```

The query is searched 300 ms after the user stops typing, and not when the Field is merely focused, touched or left. Compare with `form.query.addListener`, which also fires when the Field is touched.

## Builder, Listener and Selector

The three widgets exist for Fields, Field Arrays and Forms, and they mean the same everywhere:

- **Builder.** `builder(context, state)`. The first frame uses the current state. `buildWhen(previous, next)` receives two states and decides whether to rebuild. Without it every state change rebuilds.
- **Listener.** `listener(context, state)`, never for the state present when it is built. `listenWhen(previous, next)` decides whether to call it. Without it every state change calls it.
- **Selector.** `selector(state)` picks a value `R`. The widget rebuilds only when the picked value changes (`==`). The optional `buildWhen(previousR, nextR)` receives the previous and the next picked value and can still veto the rebuild.

## Field widgets

Field widgets always take the Field handle.

```dart
FormidableFieldBuilder<String>(
  field: form.username,
  buildWhen: (previous, current) => previous.status != current.status,
  builder: (context, state) => Text(state.status.name),
)

FormidableFieldListener<String>(
  field: form.username,
  listenWhen: (previous, current) => !previous.touched && current.touched,
  listener: (context, state) => log('left the username'),
  child: ...,
)

FormidableFieldSelector<String, bool>(
  field: form.username,
  selector: (state) => state.errors.isNotEmpty,
  builder: (context, hasErrors) => ...,
)
```

## Form widgets

The generator writes three typed widgets next to the Form Scope, in `*.formidable_scope.dart`. They need no type arguments, and the builder gets the generated state:

```dart
SignUpFormBuilder(
  builder: (context, SignUpFormState state) =>
      Text(state.username.valueOrNull ?? ''),
)

SignUpFormListener(
  listenWhen: (previous, next) => previous.meta.status != next.meta.status,
  listener: (context, state) => log('${state.meta.status}'),
  child: ...,
)

SignUpFormSelector<bool>(
  selector: (state) => state.meta.valid,
  builder: (context, canSubmit) => FilledButton(
    onPressed: canSubmit ? () => save(context.signUpForm.value) : null,
    child: const Text('Sign up'),
  ),
)
```

Each takes an optional `form`. Without one it looks up the closest `SignUpFormScope`, and throws an error that names the missing scope when there is none. `SignUpFormSelector` rebuilds only when the selected value changes, so a selector on `state.meta.valid` enables a button when the Form can be submitted and does not rebuild while the user types. The button is off while an asynchronous check runs, because a pending Form is not `valid`: select `state.meta.pending` too to show progress, see [Submit patterns](/guides/submit-patterns#show-progress-while-a-check-runs).

For code that does not use the generator, `FormidableFormBuilder<SignUpForm>`, `FormidableFormListener<SignUpForm>` and `FormidableFormSelector<SignUpForm, R>` do the same with the state typed as `FormidableFormState`, so you read `state.meta.status` there too. `FormidableTypedFormBuilder<SignUpForm, SignUpFormState>` and its Listener and Selector are what the generated widgets extend; use them to get the typed state without the generated widgets.

## Field Array widgets

`FormidableFieldArrayBuilder`, `FormidableFieldArrayListener` and `FormidableFieldArraySelector` take the array. The state they get is the `FormidableFieldArrayState<S>` of the array, which holds the state of every item, so they follow an edit of an item too. The builder keeps handing out the keyed item widgets, see [Field Arrays](/schema/field-arrays#the-field-array-builder).

```dart
FormidableFieldArraySelector(
  array: form.phones,
  selector: (state) => state.length,
  builder: (context, count) => Text('$count phones'),
)
```

## Form Scope

`SignUpFormScope` creates the Form and disposes it. To expose a Form that you own, for example one created in your page state, use the `.value` constructor. The scope never disposes it:

```dart
SignUpFormScope.value(
  form: _form,
  child: ...,
)
```

Both take exactly one of `child` and `builder`. The builder receives the Form and a context below the scope, so the Form is usable right away:

```dart
SignUpFormScope(
  builder: (context, form) => Column(
    children: [
      FormidableMaterialTextField(field: form.username),
      // `context` is below the scope, so context.signUpForm works too.
    ],
  ),
)
```

Inside a scope, `context.signUpForm` returns the Form. If the scope has been given another Form, the Form widgets pick it up.
